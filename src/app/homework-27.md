value будет равен ['A', 'B'] тк флаг multi: true меняет поведение: вместо перезаписи Angular собирает значения всех провайдеров с этим токеном в единый массив. Задача №13. ⭐
Запрос inject(A) инициирует цепочку разрешения зависимостей сверху вниз: A требует B, B требует C, C требует D, D требует LoggerService. Но реальное создание объектов происходит в обратном порядке — снизу вверх, так как каждый класс не может завершить свою инициализацию, пока не получит готовую зависимость.

1. inject(A) — Angular проверяет root injector, кэша нет, начинает создание A.
2. Внутри A встречается inject(B) — процесс уходит вглубь к B, создание A приостановлено.
3. Внутри B — inject(C), уходим к C.
4. Внутри C — inject(D), уходим к D.
5. Внутри D — inject(LoggerService). У LoggerService нет собственных зависимостей — это конец цепочки.
6. Angular создаёт LoggerService и сразу кэширует его на root injector.
7. Возврат на уровень D: поле logger получено, D полностью инициализирован и кэшируется.
8. Возврат на уровень C: поле d получено, C полностью инициализирован и кэшируется.
9. Возврат на уровень B: поле c получено, B полностью инициализирован и кэшируется.
10. Возврат на уровень A: поле b получено, A полностью инициализирован и кэшируется.
11. inject(A) возвращает готовый объект A вызывающему коду.

Задача №14. ⭐⭐
До какого-либо inject(): 0 объектов сервисов в памяти.
тк ангуляр создает лениво сервисы а инжектов не было соответсвенно 0 обьктов

После inject(UserService): появится 3 новых объекта.
Цепочка зависимостей: UserService → ApiService → LoggerService. Как и в Задаче №13, создание идёт "изнутри наружу" — Angular сначала уходит вглубь цепочки, и реально создаёт объекты в обратном порядке:
1. LoggerService создаётся и кэшируется первым.
2. ApiService получает готовый LoggerService, создаётся и кэшируется.
3. UserService получает готовый ApiService, создаётся и кэшируется.
Итог: 3 новых объекта — LoggerService, ApiService, UserService.

Задача №15. ⭐⭐⭐
1. ApiService — providedIn: 'root'. HTTP-логика и состояние должны быть едиными для всего приложения; создание отдельного экземпляра на каждый компонент привело бы к дублированию и потере консистентности
2. AuthService — providedIn: 'root'. Текущий пользователь — это глобальное состояние, которое должно быть видно на всех страницах. Локальная регистрация приводила бы к тому, что логин на одной странице терялся бы при переходе на другую.
3. CartService — providedIn: 'root'. Корзина должна сохраняться при навигации между страницами, то есть жить дольше одной страницы — весь сеанс работы приложения.
4. ProductFilterService - providers роутинга. фильтры должны жить ровно столько, сколько активен конкретный раздел каталога, и полностью уничтожаться при уходе с него. Использование providers роутинга привязывает жизненный цикл сервиса к EnvironmentInjector конкретного маршрута. Это позволяет автоматически уничтожать стейт фильтров при переходе на другой роут, но при этом безопасно делиться этим состоянием со всеми дочерними компонентами и вкладками внутри текущего маршрута
5. NotificationService - providedIn: 'root'. Toast-уведомления должны отображаться поверх любого интерфейса в приложении. Сервис обязан быть доступен из любой точки для вызова всплывающих сообщений из единого глобального центра.
6. ThemeService - providedIn: 'root'. Тема оформления — это единое глобальное состояние, которое применяется ко всему приложению одновременно. Все страницы должны синхронно реагировать на изменение темы, что требует наличия строго одного общего экземпляра сервиса.
7. DashboardStatisticsService - providers компонента (или providers роутинга). Сервис выполняет узкоспециализированную задачу — загрузку данных для конкретного экрана. Регистрация в providers компонента DashboardComponent (или его роута) гарантирует, что сервис будет создан только при открытии дашборда и автоматически уничтожен при уходе пользователя с этой страницы, не засоряя память приложения.
8. UserTableStateService - providers компонента. Данный сервис хранит уникальное UI-состояние конкретной таблицы (сортировку, пагинацию). Чтобы избежать конфликтов и взаимовлияния, каждый экземпляр компонента таблицы должен иметь свой собственный изолированный экземпляр сервиса.
9. ModalService - providedIn: 'root'. Возможность открыть модальное окно должна быть доступна из любого компонента приложения. Единый глобальный экземпляр гарантирует, что состояние isModalOpen() останется консистентным и управляемым из любой точки.
10. LoggerService - useFactory (в связке с providedIn: 'root'). Нам нужно динамически переключать поведение сервиса в зависимости от окружения (environment).
11. AppConfig - useValue (в связке с InjectionToken). Конфигурация приложения — это статичный объект. Так как у интерфейсов нет представления в рантайме, мы создаем InjectionToken<AppConfig> и регистрируем его через useValue, передавая туда сам объект с настройками.
12. CurrencyFormatter - useFactory. Форматирование валют напрямую зависит от локали пользователя или настроек системы, которые могут подгружаться динамически. С помощью useFactory мы можем заинжектить LocaleService и вернуть настроенный экземпляр форматировщика под конкретную страну.
13. AnalyticsService - useFactory. Позволяет динамически проверить флаг в конфигурации приложения. Если аналитика включена, фабрика инициализирует и возвращает полноценный рабочий сервис. Если отключена — то предотвращает загрузку
